Início / Fail path / C22

C22 — Cliente com SDK ou versão não suportada

Fail path
Status na fonte: ✅ Atualizado (modelo v1)

1. Visão geral do cenário

Só são aceitos AWS SDK Java 2.x, Go v2 e .NET v4. A versão é identificada pelo User-Agent (proteção contra configuração errada, não segurança; quem pode escrever o quê é decidido pelo certificado de cliente, C34). Há um período de 2 a 4 semanas só com alerta; depois, o desconhecido é rejeitado com HTTP 400 não retentável.

2. Diagrama

flowchart TD
    A["Requisição chega"] --> B{"User-Agent reconhecido?"}
    B -->|"sim, família e versão suportadas"| C["segue o fluxo"]
    B -->|"sim, versão mais nova que a testada"| D["segue, só alerta"]
    B -->|"sim, versão antiga ou família antiga"| E{"Período só de alerta acabou?"}
    B -->|"não"| E
    E -->|"não"| F["segue e conta rejected_client_version"]
    E -->|"sim"| G["HTTP 400 UnsupportedClientVersion, sem retry"]

3. Legenda e etapas

  1. Casar o User-Agent por trecho, não por igualdade (frameworks acrescentam texto).
  2. Go: o "v2" está no nome do módulo; os números de versão do v2 são 1.x. A regra casa pela família.
  3. .NET: o pacote AWSSDK.DynamoDBv2 tem "v2" no nome por causa da API do DynamoDB; vale somente a geração v4 do SDK.
  4. A métrica rejected_client_version{sdk,version} mostra quem ainda usa versão antiga antes da regra ativar.

1Suíte de compatibilidade com os três SDKs e inventário do cliente Pontos em aberto

Contexto
Só são aceitos AWS SDK Java 2.x, Go v2 e .NET v4, e o DataReplication precisa se comportar como o DynamoDB para eles, inclusive com o cliente HTTP apresentando certificado de cliente (mTLS). A premissa de só trocar o endpoint deixou de valer, e sem o inventário real de chamadas e parâmetros um cliente pode entrar usando algo fora da API da v1. Uma incompatibilidade descoberta em produção vira erro ou, pior, comportamento divergente silencioso.
O que a fonte define
A fonte define a suíte X3 contra o DataReplication, o DynamoDB real e o Cosmos pelo Cloud-Adapter, e exige o inventário do cliente antes de ele entrar (PEND-15, ADR-051); o User-Agent é usado só como proteção contra configuração errada, com período só de alerta antes de rejeitar com 400.
Sugestão de encaminhamento (inferência, não decidida)
Tornar a suíte X3 bloqueante no pipeline de release e por cliente, comparando respostas e códigos de erro com o DynamoDB real, e incluir casos de User-Agent alterado por frameworks. Usar a métrica rejected_client_version durante o período de alerta como critério objetivo para ativar a rejeição.
