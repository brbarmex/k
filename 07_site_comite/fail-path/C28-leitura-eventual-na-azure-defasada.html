Início / Fail path / C28

C28 — Leitura eventual na Azure durante a degradação (antes R04)

Fail path
Status na fonte: ✅ Atualizado (decidido pelo Bruno em 13/10/2026)
Relacionados: C32, C05, C12, X02

1. Visão geral do cenário

No modo degradado a Azure deixa de receber entradas. Uma leitura eventual servida por uma célula Azure lê o Cosmos local e pode devolver dado atrasado sem que o cliente saiba. Com o lease do modo degradado (ADR-044) a AWS para de aceitar escrita ao fim de D, então a defasagem de dados novos tem um teto de cerca de D, a menos que uma pessoa prorrogue (RENEW); se a Azure ficar horas fora com o lease prorrogado, o atraso volta a crescer. Para um banco, isso pode ser um saldo antigo apresentado como atual.

O padrão de leitura é forte (READ_MODE_DEFAULT, só na tabela base); este caso só ocorre quando o cliente pede leitura eventual de forma explícita, ou lê um GSI, que é sempre eventual (C05). O Eventual é só de leitura na v1: não existe apply paralelo de escrita (ADR-053). Com DEGRADED_POLICY=reject a Azure nunca fica defasada por degradação, só por lentidão.

Decisão registrada na fonte

Acima do limite de defasagem, a leitura é redirecionada à AWS se possível; senão é recusada.

3. Legenda e etapas

  1. A defasagem é max(idade do último heartbeat da líder, tempo estimado para aplicar o que já chegou), medida com relógio monotônico local, sem depender do relógio da AWS (H9).
  2. Quando o link caiu, a defasagem é desconhecida, e desconhecida conta como acima do limite.
  3. Toda resposta eventual da Azure devolve x-dr-observed-index e x-dr-staleness-ms (e x-dr-consistency: eventual em GSI); a aplicação decide se serve.
  4. MAX_STALENESS é configuração obrigatória por tabela ou global (valor inicial sugerido: 5 s, a medir).

4. Pontos que precisam ser avaliados

Reescritos a partir das seções “Falhas e tratativas” e “Pontos em aberto” (e de outras seções de risco, quando existem). Em cada ponto, O que a fonte define vem da documentação; Sugestão de encaminhamento é inferência do arquiteto, não decisão registrada.

1Redirecionar para a AWS justo quando o link está ruim Falhas e tratativas

Contexto
Acima do limite de defasagem, a leitura eventual na Azure é redirecionada à AWS, mas o encaminhamento usa o mesmo link que pode ser a causa da degradação. Retries infinitos agravariam a carga no link e poderiam competir com a replicação, piorando o gate. O resultado seria transformar um problema de leitura em latência de escrita.
O que a fonte define
Decidido no ADR-040: o fallback é redirecionar com limite de 3 s e, se não for possível, erro recuperável 503 com retryAfter, não retry infinito.
Sugestão de encaminhamento (inferência, não decidida)
Medir em teste de caos com link lento o impacto das leituras redirecionadas no gate e alertar sobre a taxa de leituras redirecionadas.

2Degradação típica com link caído: leitura eventual falha Falhas e tratativas

Contexto
Quando a degradação é por link caído, que é o caso típico, a defasagem fica desconhecida e conta como acima do limite, e não há como redirecionar à AWS. A leitura eventual na Azure então falha. É a escolha deliberada de preferir erro ao saldo antigo, mas reduz a disponibilidade de leitura para quem dependia da Azure durante o degradado.
O que a fonte define
Decidido no ADR-040: a leitura falha com 503 em vez de devolver dado velho; a aplicação precisa tratar o erro.
Sugestão de encaminhamento (inferência, não decidida)
Informar explicitamente os clientes que usam leitura eventual ou GSI na Azure e exigir no inventário (PEND-15) como cada um trata o 503. Incluir o caso na suíte de compatibilidade e em game day com o link cortado, medindo a taxa de erro de leitura.

3Clientes que ignoram os cabeçalhos de defasagem Falhas e tratativas

Contexto
Dentro do limite, as respostas eventuais da Azure devolvem x-dr-observed-index e x-dr-staleness-ms, e a aplicação decide se serve o dado. O cabeçalho informa, não impede. Um cliente que ignora os cabeçalhos pode apresentar dado defasado como atual, por exemplo um saldo, sem que a camada perceba.
O que a fonte define
A fonte diz que o cliente que nunca pode ler dado velho deve usar leitura forte.
Sugestão de encaminhamento (inferência, não decidida)
Mapear no inventário (PEND-15) quem usa leitura eventual e GSI e confirmar que leem os cabeçalhos ou aceitam a defasagem.

4Defasagem depois da promoção da Azure Falhas e tratativas

Contexto
Após a promoção, a Azure vira a líder e a defasagem passa a ser medida contra ela mesma. O limite deixa de se aplicar à Azure e passa a valer para as células que forem learners, inclusive as AWS que voltarem. Se o cálculo não trocar de referência com a epoch, a Azure promovida poderia recusar leituras sem motivo ou uma célula AWS defasada poderia servi-las.
O que a fonte define
Decidido na fonte, em coerência com o C14.
Sugestão de encaminhamento (inferência, não decidida)
Incluir na validação pós-promoção um teste de que o cálculo de defasagem troca de referência com a epoch.

5Valor inicial de MAX_STALENESS Pontos em aberto

Contexto
MAX_STALENESS é configuração obrigatória por tabela ou global e define quando a leitura eventual na Azure é recusada ou redirecionada. O valor inicial é só uma sugestão de 5 s, a medir. Um valor baixo demais gera 503 ou redirecionamentos mesmo em operação normal; um alto demais expõe dado velho.
O que a fonte define
Não decidido na fonte. Proposta na fonte: 5 s, ajustado depois do spike.
Sugestão de encaminhamento (inferência, não decidida)
Medir no spike a distribuição do lag normal de apply no Cosmos e definir o valor por tabela com os clientes, acima do P99 do lag normal para não gerar recusas espúrias. Alertar sobre a taxa de leituras recusadas ou redirecionadas por tabela.

Falhas e tratativas
  • Redirecionar para a AWS justo quando o link está ruim. O encaminhamento usa o link que pode ser a causa da degradação. Por isso o fallback é erro recuperável, não retry infinito.
  • Degradação típica = link caído. Nesse caso não há como redirecionar e a leitura eventual na Azure falha em vez de devolver dado velho. É a escolha deliberada de preferir o erro ao saldo antigo; a aplicação que dependia da Azure para ler precisa tratar o 503.
  • Clientes que ignoram o cabeçalho. O cabeçalho informa, não impede. Para dado que nunca pode ser velho, o cliente deve usar leitura forte.
  • Depois da promoção da Azure. A Azure vira a líder (C14) e a defasagem passa a ser medida contra ela mesma; o limite deixa de se aplicar à Azure e passa a valer para as células que forem learners.
Pontos em aberto
  • Valor inicial de MAX_STALENESS (sugestão: 5 s), ajustado depois do spike.
